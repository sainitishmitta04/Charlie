Phase 8 Voice Refinement — Deterministic Command Normalization

The Phase 8 conversation mode is now working.

However, real voice testing revealed that conversational follow-up commands are incorrectly being interpreted as TYPE_TEXT.

DO NOT start Phase 9.
DO NOT implement Laya.
DO NOT redesign the conversation state machine.

This is a focused Phase 8 refinement.

==================================================
CURRENT PROBLEM
==================================================

Running:

PYTHONPATH=backend python -m app.main --wake-word

I tested:

"Charlie, open Apple Notes"

This correctly opens Notes.

Then conversation mode becomes active.

However:

"Enter"

is transcribed as:

"Enter."

and becomes:

TYPE_TEXT
Target: Enter.

This causes the word "Enter." to be typed into Notes.

Similarly:

"Next line."

becomes:

TYPE_TEXT
Target: Next line.

Instead it must become:

PRESS_KEY
Target: Enter

Other spoken commands are also being treated as text when they should be interpreted as commands.

==================================================
IMPORTANT OBSERVATION
==================================================

Whisper transcription is NOT the main problem.

The transcripts are often semantically clear:

"Enter."
"Next line."
"press enter"

The problem is that command normalization/classification is happening too late or not deterministically enough.

We need a lightweight deterministic command-normalization layer BEFORE Jev whenever the intent is unambiguous.

==================================================
DESIRED PIPELINE
==================================================

Current:

Whisper
  ↓
Jev
  ↓
Structured Action


Change to:

Whisper
  ↓
Normalize transcript
  ↓
Deterministic command matching
  ↓
If confidently recognized:
    Structured Action
  ↓
Otherwise:
    Jev
  ↓
Structured Action
  ↓
Validation
  ↓
Executor


Do NOT bypass Jev for normal natural-language commands.

Only bypass Jev for a small, explicit allowlist of deterministic commands.

==================================================
1. NORMALIZATION
==================================================

Create a small normalization function/module if one does not already exist.

For example:

normalize_voice_command()

It should:

- strip leading/trailing whitespace
- normalize repeated whitespace
- normalize case for command matching
- safely strip terminal punctuation for command matching

Examples:

"Enter."
"ENTER!"
"enter?"
" Enter "

should all match:

"enter"

But IMPORTANT:

Do NOT modify the actual text when the command is going to TYPE_TEXT.

The normalized form is only for intent matching.

For example:

"Hello, world!"

must remain exactly:

"Hello, world!"

when sent to TYPE_TEXT.

==================================================
3. ARROW KEYS
==================================================

Also support the existing safe keyboard action for:

"up"
"arrow up"
"press arrow up"

"down"
"arrow down"
"press arrow down"

Only exact/strong command phrases should match.

For example:

"right"

"press right arrow"

can be treated as keyboard commands.

==================================================
4. COMMAND MATCHING MUST BE EXACT
==================================================

This is VERY IMPORTANT.

Do not use substring matching.

Bad:

if "enter" in transcript:
    PRESS_KEY Enter

That would incorrectly interpret:

"enter the grocery list"

as Enter.

Instead use exact normalized phrases.

Example:

normalized == "enter"

or:

normalized in {
    "press enter",
    "hit enter",
    "enter"
}

Only then return PRESS_KEY.

==================================================
5. "NEXT LINE"
==================================================

Treat:

"next line"
"new line"

as:

PRESS_KEY
Enter

This is especially important for Notes.

Example:

"Charlie, open Notes"

"Grocery List"

"next line"

"Eggs"

should result in:

Grocery List
Eggs

Do not type the words "next line".

==================================================
6. CONVERSATIONAL FILLERS
==================================================

Whisper sometimes produces conversational fillers.

Example:

User intended:

"Grocery List"

Whisper:

"Right, grocery list?"

The existing implementation already removes some obvious filler.

Make this normalization conservative.

Safe examples:

"right, grocery list?"

→ "grocery list?"

"okay, grocery list"

→ "grocery list"

"ok, grocery list"

→ "grocery list"

"alright, grocery list"

→ "grocery list"

But DO NOT strip words blindly.

For example:

"right arrow"

must remain:

"right arrow"

because it is a keyboard command.

"right click"

must remain:

"right click"

Do not implement broad fuzzy correction.

==================================================
7. IMPORTANT: DO NOT CORRECT CONTENT
==================================================

The normalization layer is for COMMAND DETECTION only.

Do NOT convert:

"grocery list?"

into:

"Grocery List"

automatically.

If Jev decides this is TYPE_TEXT, preserve the transcript's actual content unless existing behavior intentionally normalizes it.

The command layer should not silently rewrite user text.

FINAL GOAL
==================================================

The key principle is:

If a voice command is an exact, deterministic, safe keyboard/control command,
handle it locally.

Otherwise:

send it through the existing decision engine.

Architecture:

Microphone
    ↓
Wake/Conversation State
    ↓
Whisper
    ↓
Transcript Normalization
    ↓
Deterministic Command Matcher
    │
    ├── recognized → Structured Action
    │
    └── unknown → JevDecisionEngine
                       ↓
                 Structured Action
                       ↓
                   Validation
                       ↓
                   Executor
                       ↓
                Context Update

Do not make the deterministic matcher overly intelligent.

Keep it small, explicit, testable, and safe.
